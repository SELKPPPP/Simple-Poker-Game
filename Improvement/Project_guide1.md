# Agent 工作规则

> **这个文档的用途**：告诉 agent（包括未来每个新开的 Claude session）每次工作时必须遵守的规则。
>
> **配套文档**（开始任何工作前都该知道它们在哪）：
> - `项目知识库.md` —— 项目用到的所有概念背景（博弈论、CFR、游戏规则、工程概念、术语对照）
> - `model_improvement_plan.md` —— 当前生效的方案（"现在该做什么"）
> - `CHANGELOG.md` —— 所有版本演进的历史记录（"过去怎么来的"）

---

### 规则 1：任何改动都要更新 CHANGELOG.md

**为什么**：方案演进过 3 版（v1 Q-learning → v2 CFR → v3 Local+Fold），Phase 0 又改了 3 版。没有 CHANGELOG，下次打开根本想不起来"为什么 fold 要在 redraw 前面"这种关键设计决策。

**怎么做**：
- 改了方案文档、改了代码、删了文件、做了非平凡的设计决策 → 在 `Improvement/CHANGELOG.md` **顶部**加新条目
- 用模板：
  ```
  ## YYYY-MM-DD — <主题简述>
  **触发**：为什么要改
  **改动**：具体改了什么
  **测试**：测试变化（pass / 新增 / 删除）
  **文件**：相关文件清单
  ```
- 旧条目不删不改，只在顶部加新的

### 规则 2：开始任何 Phase 之前先把三份文档过一遍

- `项目知识库.md` —— 不懂某个术语 / 概念 / 设计原因时跳到对应章节
- `model_improvement_plan.md` —— 当前方案快照，确认这个 Phase 要做什么
- `CHANGELOG.md` —— 看最近 3-5 条，了解上一个 session 在做什么

### 规则 3：遵守 `CLAUDE.md` 的四条准则

1. **Think Before Coding** —— 不假设、不藏疑问、显式列出权衡
2. **Simplicity First** —— 没人要的功能、没人要的抽象、没人要的灵活性，都别加
3. **Surgical Changes** —— 只改用户要求的东西，别"顺便"美化无关代码
4. **Goal-Driven Execution** —— 每个任务定可验证的成功标准（不是"让它能跑"这种废话）

### 规则 4：每完成一个 Phase，要求用户确认才进下一个 Phase

不要自作主张连着做多个 Phase。每个 Phase 完成后停下来，告诉用户：
- 完成了什么（具体哪些文件、哪些测试通过）
- 下一个 Phase 是什么、要多久、要做什么
- **等用户说"开始"**

### 规则 5：本项目范围严格限制在 `cfr/` 目录

**不动 backend (`Backend/`)、frontend (`Frontend/`)、DB、原 `model/`**。这是 v3 方案明确的范围决策（参见 CHANGELOG 2026-05-20 方案 v3 条目）。

### 规则 6：引入新概念 / 新设计时要更新 `项目知识库.md`

**为什么**：`项目知识库.md` 是未来新 session 理解项目的入口。新概念没记进去，下次 agent 上来就不知道这个概念在项目里是什么角色，又得用户重新教一遍。

**怎么做**：
- 实现 Phase 2/3/4 时引入了新东西（比如具体的 chance node 处理方式、checkpoint 格式、eval 指标定义）→ 加到 `项目知识库.md` 对应章节
- 改了游戏规则 → 更新 `项目知识库.md` §4「游戏规则与设计」
- 新增工程做法 → 更新 `项目知识库.md` §5「工程概念」
- 同步更新附录 A 的术语对照表

**和 CHANGELOG 的区别**（两边都要记，角度不同）：
| 文档 | 记什么 | 视角 |
|---|---|---|
| `CHANGELOG.md` | 做了什么改动 | 事件流（按时间） |
| `项目知识库.md` | 项目当前用到的概念和决策 | 当前状态快照 |
